

Task: Align Quarto Manuals with an operator-manual cognitive model

Objective

Revise the Quarto Manuals repository so that its documentation, templates, and examples consistently communicate the following design principle:

A Quarto Manual is an executable operator’s manual, not a tutorial.

The intended reader is a competent practitioner in the relevant domain. A manual should make the operations, decisions, required inputs, visible state transitions, and verification points explicit without routinely teaching the underlying concepts.

The useful cognitive model is similar to a high-quality assembly or equipment manual: establish the current state, identify what is needed, perform the next transformation, verify the resulting state, and continue.

LEGO instructions are a useful design analogy for reasoning about this task, but do not make LEGO the branding, central metaphor, or conceptual foundation of Quarto Manuals. It may be mentioned sparingly, if at all. Extract the interaction principles rather than centering the commercial product.

IMPORTANT: the US-RSE abstract content and other material under `pubs` is accepted scientific material. **DO NOT modify scientific abstracts.** Suggest changes adjadently that a human will integrate.

Core design principles to encode

Treat these as repository-wide authoring rules.

1. Explicitness is not pedagogy

A procedure may be extremely explicit while containing almost no conceptual explanation.

Prefer:

Create config/, then write config/manual.json.

over:

A configuration directory is a common software-engineering pattern used to…

Do not explain standard domain concepts merely because they appear in a procedure.

2. Assume a competent operator

Each manual has an implied operator who already knows the ordinary vocabulary and basic tools of that workflow.

A research-computing manual may assume the reader understands concepts such as files, directories, shells, data frames, package managers, or schedulers when those are ordinary prerequisites for that workflow.

Do not turn routine operations into beginner lessons.

If unusual prerequisite knowledge is genuinely necessary, either state it briefly as a prerequisite or provide narrowly scoped supporting material.

3. The fundamental unit is an observable state transition

Think of each procedure step as:

known state → operator action → observable new state

A useful page should expose the transformations necessary to move the workflow forward.

The existing page contract already maps well onto this:

* manual-prereq: establish or verify the starting state;
* manual-procedure: perform one or more necessary transformations;
* manual-check: verify the resulting state.

Preserve this architecture.

4. Explain by exception

Conceptual explanation should not be the default content of a procedure.

Provide extra explanation when something is:

* unusual or domain-specific;
* easy to misinterpret;
* safety- or correctness-critical;
* surprising despite normal domain competence;
* dependent on behavior that is not obvious from the operation itself.

The analogy is an instruction manual using an enlarged inset or warning only when an unusual component or orientation needs special attention.

Do not turn this into a requirement to add explanatory material everywhere.

5. Automate mechanics, preserve decisions

Automation is encouraged when multiple operations are mechanical and no meaningful operator judgment occurs between them.

It is acceptable for a manual procedure to invoke a script, CLI, workflow engine, package, or agent.

However, automation must not hide:

* meaningful operator decisions;
* required inputs;
* consequential parameters;
* observable state transitions;
* verification points.

Do not expand every automated operation into a teaching exercise merely for the sake of visibility.

Conversely, do not collapse a workflow into a single opaque command when the operator genuinely needs to inspect or decide something between stages.

6. Prefer the smallest reliable sequence of operations

Do not maximize either prose or automation.

Decompose the workflow only far enough that a competent operator can execute, inspect, and recover the procedure reliably.

A manual should not say merely:

Configure the environment.

if that hides several consequential operations.

But it also should not explain package management, environment variables, filesystem semantics, and dependency resolution unless those concepts are specifically relevant to this procedure.

7. Software should not be surprising

The operator should be able to anticipate what a procedure will consume, what it will do, and what state it should leave behind.

Use the manual to reduce surprise by making consequential operations and boundaries visible.

Do not use it to narrate every implementation detail.

3. Authoring template

Update both:

* 10_page-<task>.qmd
* site/10_page-tasks.qmd

They should remain synchronized in philosophy.

Add concise authoring guidance before or around the page contract.

Explicitly tell authors and LLMs:

Write for a competent operator.

Describe the action and the expected state, not the textbook concept behind the action.

Add explanation only when ordinary domain knowledge is insufficient to execute the step correctly.

For each block, clarify its semantic role.

Prerequisite

Its job is to establish whether the required starting state exists.

It should not normally teach the tools being checked.

Procedure

Its job is to change project/system state.

Procedure prose should emphasize:

* what the operator must supply;
* what command/code/action to perform;
* consequential choices;
* what artifact or state change should result.

Avoid tutorial exposition by default.

Check

Its job is to provide observable evidence that the intended transformation occurred.

A check should answer:

What should now be true?

not:

What concept should the reader have learned?

4. Optional explanation mechanism

Investigate whether the project should formally recognize an optional semantic concept such as .manual-explain.

Do not automatically build substantial new infrastructure for it.

First determine whether a semantic block would materially improve authoring and rendering.

If adding it is simple and consistent with the extension architecture, its semantics should be:

Optional, exceptional explanatory context needed to execute or interpret an otherwise operational step.

It must not become a required fourth part of every page.

The required page contract remains:

1. one prerequisite;
2. one or more procedures;
3. one check.

If implementing .manual-explain would require disproportionate extension complexity, document the convention instead and leave implementation for future work.

Record the decision in the change summary.

If yes, retain or improve it.

Ensure examples demonstrate several important cases:

Straightforward operation

Show a terse sequence where the action is already familiar and requires almost no explanation.

Consequential choice

Show a case where the operator must choose a parameter, path, strategy, resource level, or other meaningful option. Make that decision explicit rather than automating it away.

Mechanical automation

Show that a script or tool may legitimately absorb multiple mechanical substeps when no human decision is needed between them.

Do not unpack the script into tutorial prose merely to make the page longer.

Exceptional explanation

Find at least one genuinely unusual or non-obvious operation in the intermediate or advanced examples.

Provide a small amount of targeted explanation there so that the repository demonstrates that explanation is allowed when justified.

This should feel like an exception, not the default style.

Verification

Make checks concrete and state-oriented wherever possible.

Prefer verifying files, directories, metadata, command results, tests, configuration, or other observable project state.

When generating or revising a Quarto Manual, do not treat explicitness as a request for pedagogy. Assume the intended operator possesses ordinary domain competence. Style constraints

Do not make LEGO a major theme.

A brief acknowledgement in author/design documentation is acceptable if genuinely useful, but the resulting product should stand on general principles of instructional and operational design.

Avoid phrases suggesting that the Manual’s goal is to “teach users programming,” “walk beginners through concepts,” or otherwise imply that every manual is pedagogical.

Avoid the opposite extreme as well: Manuals should remain readable to humans and should not degenerate into uncommented shell scripts.

Prefer imperative, operational prose.

Examples:

Good:

Set partition to the Slurm partition you intend to use.

Good:

Run the emitted test suite before continuing.

Good:

Inspect the generated manifest. Confirm that the expected 12 files are present.

Usually unnecessary:

Slurm is a workload manager commonly used on HPC systems…

Usually unnecessary:

JSON is a text-based data-interchange format…

Appropriate exceptional explanation:

This cluster mounts $HOME differently inside batch jobs, so the container bind must use the project path rather than the interactive-session path.

The last example explains a non-obvious fact because it materially changes the correct operation.

⸻

Preserve existing architectural boundaries

Do not turn Quarto Manuals into:

* a workflow engine;
* a state database;
* a required helper library;
* a replacement for Snakemake, Nextflow, Slurm, targets, or ordinary scripts;
* a tutorial framework.

Preserve page independence and visible filesystem/project state.

Preserve the separation between Quarto Manual semantics and quarto-emit.

quarto-emit may materialize artifacts; the Manual describes and governs the operator-facing procedure in which those artifacts are created or used.

Acceptance criteria

The work is complete when a new reader—or an LLM authoring against the repository—would reasonably infer all of the following without needing this task file:

1. A Quarto Manual is an operator’s manual, not inherently a tutorial.
2. Its assumed audience is a competent practitioner for the workflow.
3. A page primarily represents an observable state transition.
4. Prerequisite, procedure, and check correspond to before/action/after.
5. Conceptual explanation is optional and exception-driven.
6. Mechanical work may be automated.
7. Meaningful human decisions and verification boundaries should remain visible.
8. Explicit instructions do not imply explaining standard concepts.
9. Examples visibly demonstrate terse operations, meaningful choices, automation, exceptional explanation, and verification.
10. The README, website, templates, examples, and US-RSE manuscript use compatible language.
